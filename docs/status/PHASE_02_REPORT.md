# Phase 02：确定性地形核心

## 阶段目标

建立引擎无关、可回放、可验证且受性能边界约束的权威地形系统。相同初始地形与操作序列必须得到一致的材料变化、支撑关系、坍塌事件、检查点和最终状态哈希；运行时局部修改不得退化为每帧全图重算。

## 主要实现

- `@skymenders/terrain-core`：32×32 Chunk、扁平整数栅格、四种材料、完整性、破坏、修复、固定锚点、构造支撑、局部支撑计算、刚性块坍塌、地图校验和操作回放。
- 地形状态限制在 32,768 单元以内，材料码、完整性、根节点、脏 Chunk 和修订号均执行运行时不变量校验。
- 破坏使用受限整数圆形掩码并按硬度计算；修复验证材料兼容、能源和实际增量；能源晶体破坏释放与弹性云苔缓冲均由规则数据确定。
- 支撑系统使用材料传播成本、根容量、确定性最大堆和显式平局规则；运行时从脏 Chunk 及其一格边界出发，只遍历相关连通组件。
- 坍塌先移除不稳定组件，再按稳定顺序逐块向下结算至落稳或离开地图；表现层碎屑不进入权威状态。
- 地形操作执行器为每次破坏、修复和坍塌写入状态哈希检查点，并返回排序后的材料效果、支撑分析和坍塌事件。
- 地图校验覆盖出生点、目标支撑/可达性、能力供给、导航、AI 交战区、锚点、镜头范围和首轮稳定性。

## 架构变化

ADR 0003 固化扁平栅格、左下角坐标原点、32×32 Chunk、规则化材料码、局部脏组件支撑算法和刚性垂直坍塌。Cocos 轮廓、粒子、碎屑、插值和镜头只消费权威事件，不得反向参与判定。

初始状态将所有 Chunk 标脏，以便首次生成表现；表现层消费后必须清除脏标记。之后修改只标记触及 Chunk 及接缝邻居。全图支撑计算只允许在加载、内容校验和显式诊断边界使用。

## 数据库或协议变化

未引入数据库、迁移或网络服务。独立兼容性维度变更如下：

| 维度           | 变更          | 原因                             |
| -------------- | ------------- | -------------------------------- |
| `rulesVersion` | 0.1.0 → 0.2.0 | 首个权威材料、支撑与坍塌规则契约 |

`protocolVersion` 与 `replaySchemaVersion` 保持 `0.1.0`；客户端、服务端、内容和存档版本仍为 `0.0.0`。地形操作当前是内部规则记录，Phase 3 才接入完整战斗命令与事件。

## 安全与隐私影响

本阶段不收集身份、设备或其他个人信息，不加入凭证或平台 SDK。外部构造的地形状态通过尺寸、数组、整数范围、材料码、完整性、根节点和脏 Chunk 上限校验。破坏半径、能量、根容量和地图单元数均有硬限制，避免异常输入造成无界循环或状态膨胀。

逻辑哈希仍仅用于确定性漂移和损坏检测，不被描述为反作弊签名。后续排行榜和 PvP 必须由可信服务端复算。

- 地形单元、属性、Golden 与回放测试：27 个通过。
- 覆盖四种材料、状态不变量、Chunk 接缝、破坏、修复、根重连、支撑容量、局部/全量分析、坍塌排序和落点、地图错误码、操作检查点。
- 64 组固定种子属性样例验证破坏单调性、输入不可变、重复执行相等、支撑/坍塌确定性、材料-完整性合法组合和最终哈希一致。
- Golden 大型坍塌固定损伤检查点 `3c35bec410593720`、最终状态 `bb473002eac7e50e`、事件哈希 `5ee339be9f95cdca`。

- 官方 npm 高危漏洞审计无已知漏洞；CycloneDX 1.6 SBOM 正常生成 225 个组件。

## 性能结果

192×96 地图中切断桥梁，局部支撑分析检查 2,519 个占用单元和 9 个 Chunk，随后坍塌 2,200 个单元。最新的 3 次预热、15 次计量样本为中位数 11.17 ms、p95 15.67 ms，低于 100 ms 权威任务预算。

该结果是 Node 地形权威微基准，不是 Cocos 帧率或真机性能声明。渲染、轮廓、内存和真机预算在 Phase 5/10 验证。

## 已知限制

- 坍塌权威采用刚性垂直块，不实现旋转柔体或逐碎屑物理。
- 当前地图校验验证结构、能力和标记导航可达性；完整模板生成、批量模拟、模块级可解性证明属于后续阶段。
- 地形事件尚未接入完整战斗回合、伤害、目标和模块协议，属于 Phase 3。
- 本机仍无 Docker CLI；本阶段没有新增容器依赖。
